One page that explains the whole system: where things live, the 4-folder law (0-docs first), how any AI account starts and ends a session, how alarms survive when an account stops, and how a finished product reaches its server.

1 · The picture

20 Sep 2026 · Website source, backup and GitHub rule

NAS Nizam is the master record and backup location. GitHub contains sanitized source only; PC folders are working clones.

  • EX4 runs website backup v2 at 02:30 Doha: root-only raw restore copy + clean 2-source.
  • Never put credentials, databases, server backups, private config, runtime WAV/PCM/MP4, generated cards or rolling logs in GitHub.
  • Private website repos: farooqstars-2.0, farooqmusic-website, mymandoob-website.
  • PC task Nizam-Git-Safe-Pull runs every 30 minutes: fetch + fast-forward-only pull. It never pushes, merges, resets or overwrites local work.
  • If a repository is dirty, ahead or diverged, automation writes BLOCKED and stops. Preserve unique work before cleanup.
  • Current hardware caution: if Console shows RAID recovery/resync, inspect Storage and do not reboot EX4.

2 · The folder law (every project)

0-docsFirst stop of every project. ALL its documents: .md · .txt · .docx · .pdf — nothing project-related is stored anywhere else. The NAS numbers each file 0001-, 0002-… — highest number = latest. Read them in Nizam Docs.
1-workingThe mess. Tests, downloads, half-done things. Farooq drops everything here. Can be emptied at the end.
2-sourceClean, finalized source only. The AI keeps it tidy. Nothing else is mixed in. This is what future updates start from.
3-finalThe deliverable, linked to the live server. Nobody edits it by hand. When it changes, the server updates itself. No junk may ever land here.

Where: Y:\FA-00x-name\ on the PC = \\192.168.10.28\Nizam on the NAS. Plus _archive (never delete — archive) and _nizam (the record, kept in git, not on Y:).

3 · The record — 6 small files per project

FileWhat it isWho writes
STATUS.mdOne live page: "Now", "Next", decisions, never-do listthe AI at the end of each session
LOG.mdAppend-only line per event: date · badge · CLAIM/DONE/BLOCKED/HANDOFF/NOTE · text · evidenceevery AI, the gateway, the NAS cron
TASKS.jsonTasks with state, owner, phase, day, gate, evidenceAI / Console buttons
PLAN.mdPhases with gates (gate over date), finish lineAI (imported from a project's own plan)
SCHEDULE.jsonAlarms of this project (see 5)gateway on every alarm run; owner pause/resume
IDEAS.md · MAINTENANCE.mdParked ideas · expiries, renewals, checksanyone

START.md / START.ur.md is built from all of these by the NAS every 15 minutes. Never hand-edit it.

4 · One session, any AI

1
READ — START (rules, all projects, open handoffs, schedules) → the project's STATUS → LOG tail.
2
CLAIM — one LOG line "CLAIM" so no other account works on the same thing.
3
WORK — inside the folder law, under the golden rules, with evidence.
4
WRITE — STRICT — update STATUS "Now / Next", append LOG "DONE" or "BLOCKED", update TASKS when needed, and write the Conversation record. Cards read STATUS + LOG; Conversation alone does not update a card.
5
HANDOFF — if it cannot finish: task state "handoff" + owner = next badge. START shows it at the top for everyone.

5 · Alarms that survive

The alarm's definition lives in SCHEDULE.json; the same prompt is installed in every account (only the badge and its token differ). Every run first asks the gateway to claim today's slot:

AnswerMeaning
okthe slot is yours — work, then close with done / failed / skip
already-claimed / already-doneanother account is on it or did it — stop silently
pausedFarooq pressed ⏸ in the Console — stop silently

Account 2 runs the same alarm 30 minutes later (watchdog). If account 1 is paused or out of credits, account 2 gets ok and continues the SAME schedule from the same record. Current alarms: FA-001 Stars daily brief (04:30 Doha) and FA-012 Kitab nightly (details to come). Urduzaban: on demand only.

6 · 3-final → server (Phase 4b)

The NAS watches every 3-final. When it changes, nizam-deploy.sh reads DEPLOY.json and pushes: ssh/rsync (Oracle over Tailscale), git push (Hostinger sites), or deploy.php (farooqstars.com). Dry-run until Farooq sets enabled: true per site. Junk in 3-final = refused + LOG line. Every deploy = one LOG line.

7 · Golden rules (short)

Never$ without a yes · a key/password/token in any file or message · deleting Farooq's files · a second Oracle VM or a reset · formatting the EX4 · hand-editing START or 3-final · changing what he did not ask
Alwaysread START first · claim before work · evidence with every "done" · two separate languages, English digits · archive instead of delete · give the commit Summary / Description in the same message

1 · پوری تصویر

20 ستمبر 2026 · website source، backup اور GitHub کا قانون

NAS Nizam مرکزی ریکارڈ اور backup جگہ ہے۔ GitHub میں صرف صاف source؛ PC folders کام کی clones ہیں۔

  • EX4 روزانہ 02:30 دوحہ website backup v2 چلاتا ہے: root-only مکمل restore copy + صاف 2-source۔
  • GitHub میں credentials، database، server backups، private config، runtime WAV/PCM/MP4، generated cards یا بدلتے logs کبھی نہ ڈالیں۔
  • نجی website repos: farooqstars-2.0، farooqmusic-website، mymandoob-website۔
  • PC task Nizam-Git-Safe-Pull ہر 30 منٹ fetch + fast-forward-only pull کرتا ہے؛ کبھی push، merge، reset یا overwrite نہیں۔
  • repository dirty، ahead یا diverged ہو تو automation BLOCKED لکھ کر رک جاتا ہے؛ صفائی سے پہلے منفرد کام محفوظ کریں۔
  • اگر Console میں RAID recovery/resync دکھے تو پہلے Storage دیکھیں؛ EX4 reboot نہ کریں۔

2 · فولڈر کا قانون (ہر پروجیکٹ)

0-docsہر پروجیکٹ کا پہلا پڑاؤ۔ اُس کی ساری دستاویزات: .md · .txt · .docx · .pdf — پروجیکٹ سے متعلق کوئی فائل کہیں اور نہیں رکھی جاتی۔ NAS ہر فائل کو 0001-، 0002-… نمبر دیتا ہے — سب سے بڑا نمبر = تازہ ترین۔ پڑھنے کے لیے Nizam Docs۔
1-workingگند۔ test، download، ادھورا کام۔ فاروق صاحب سب کچھ یہیں ڈالتے ہیں۔ آخر میں خالی کیا جا سکتا ہے۔
2-sourceصرف صاف، final source۔ AI اسے سنبھالتا ہے۔ کچھ اور اس میں نہیں ملتا۔ آئندہ update یہیں سے شروع ہوتا ہے۔
3-finalتیار product، live server سے جڑا ہوا۔ کوئی ہاتھ سے نہیں چھوتا۔ بدلے تو server خود update ہوتا ہے۔ فالتو فائل یہاں کبھی نہیں آتی۔

کہاں: PC پر Y:\FA-00x-name\ = NAS پر \\192.168.10.28\Nizam۔ ساتھ _archive (delete کبھی نہیں — archive) اور _nizam (ریکارڈ، git میں، Y: پر نہیں)۔

3 · ریکارڈ — ہر پروجیکٹ کی 6 چھوٹی فائلیں

فائلیہ کیا ہےکون لکھتا ہے
STATUS.mdایک زندہ صفحہ: "Now"، "Next"، فیصلے، کبھی-نہیں کی فہرستAI ہر نشست کے آخر میں
LOG.mdہر واقعے کی ایک سطر (صرف اضافہ): date · badge · CLAIM/DONE/BLOCKED/HANDOFF/NOTE · text · evidenceہر AI، gateway، NAS cron
TASKS.jsonکام: حالت، ذمہ دار، phase، day، gate، ثبوتAI / Console بٹن
PLAN.mdمراحل اور gates (تاریخ سے پہلے gate)، finish lineAI (پروجیکٹ کے اپنے plan سے import)
SCHEDULE.jsonاس پروجیکٹ کے alarms (حصہ 5)ہر alarm run پر gateway؛ مالک pause/resume
IDEAS.md · MAINTENANCE.mdرکھے ہوئے خیالات · expiry، renewal، جانچکوئی بھی

START.md / START.ur.md اِن سب سے NAS ہر 15 منٹ بناتا ہے۔ ہاتھ سے کبھی نہ بدلیں۔

4 · ایک نشست، کوئی بھی AI

1
READ — START (اصول، سب پروجیکٹ، کھلے handoff، schedules) → پروجیکٹ کی STATUS → LOG کا آخر۔
2
CLAIM — LOG میں ایک سطر "CLAIM" تاکہ دوسرا account وہی کام نہ اٹھائے۔
3
WORK — فولڈر قانون کے اندر، سنہری اصولوں کے تحت، ثبوت کے ساتھ۔
4
WRITE — سخت قانون — STATUS کا "Now / Next" update، LOG میں "DONE" یا "BLOCKED"، ضرورت پر TASKS، اور Conversation record لازماً لکھیں۔ Card، STATUS + LOG سے بنتا ہے؛ صرف Conversation سے card update نہیں ہوتا۔
5
HANDOFF — مکمل نہ ہو سکے تو task کی حالت "handoff" + ذمہ دار = اگلا badge۔ START سب کو اوپر دکھاتا ہے۔

5 · وہ alarms جو زندہ رہتے ہیں

alarm کی تعریف SCHEDULE.json میں ہے؛ وہی prompt ہر account میں لگا ہے (صرف badge اور اس کا token الگ)۔ ہر run پہلے gateway سے آج کا slot claim کرتا ہے:

جوابمطلب
okslot تمہارا ہے — کام کرو، پھر done / failed / skip سے بند کرو
already-claimed / already-doneدوسرا account کر رہا ہے یا کر چکا — چپ چاپ رُک جاؤ
pausedفاروق صاحب نے Console میں ⏸ دبایا — چپ چاپ رُک جاؤ

Account 2 وہی alarm 30 منٹ بعد چلاتا ہے (watchdog)۔ اگر account 1 رُکا ہو یا credits ختم ہوں تو account 2 کو ok ملتا ہے اور وہ اُسی ریکارڈ سے وہی schedule جاری رکھتا ہے۔ موجودہ alarms: FA-001 Stars daily brief (04:30 دوحہ) اور FA-012 کتاب — رات کی تحریر (تفصیل آنی ہے)۔ اردو زبان: صرف on demand۔

6 · 3-final → server (Phase 4b)

NAS ہر 3-final پر نظر رکھتا ہے۔ بدلے تو nizam-deploy.sh DEPLOY.json پڑھ کر بھیجتا ہے: ssh/rsync (Oracle، Tailscale سے)، git push (Hostinger سائٹس)، یا deploy.php (farooqstars.com)۔ جب تک فاروق صاحب ہر سائٹ پر enabled: true نہ کریں، صرف dry-run۔ 3-final میں فالتو فائل = انکار + LOG سطر۔ ہر deploy = ایک LOG سطر۔

7 · سنہری اصول (مختصر)

کبھی نہیںبغیر "ہاں" کے خرچ · کسی فائل یا پیغام میں key/password/token · فاروق صاحب کی فائل delete · دوسرا Oracle VM یا reset · EX4 format · START یا 3-final ہاتھ سے · وہ بدلنا جو نہیں کہا گیا
ہمیشہپہلے START پڑھو · کام سے پہلے claim · ہر "ہو گیا" کے ساتھ ثبوت · دو الگ زبانیں، English ہندسے · delete کی جگہ archive · commit کا Summary / Description اُسی پیغام میں
